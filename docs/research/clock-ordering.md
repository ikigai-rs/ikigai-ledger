# Clock-dependent decisions and cross-host ordering

Scope: source review of this ledger repository at the parent of this note, plus the executable proof in `tests/skew_research.rs`. The proof uses two independently clocked kernels over one in-memory store, not two physical machines or replicated stores. The judge and gonk implementations are outside this repository and were not inspected; their verdict, correction, mirror, cursor, and budget semantics remain questions, not findings. No claim here establishes how their records merge.

## Reproduction

⚠ **Since ledger #4199 this inversion is fixed for comments, `comments=last`, history and the session hand-back**: each record carries a store-allocated per-item `ledger:itemRevision` (README, "Commit order"), and `tests/skew_research.rs` is now the regression, asserting that the second write lists second. The paragraph below describes the proof as it was written against 0.26.0.

Run `cargo test --test skew_research`. The fast host's clock is 2026-09-15 00:01:00 UTC; the slow host's is 00:00:00 UTC. The fast host files an item and writes `first write`; only after that call returns, the slow host writes `second write` to the same item. Both writes succeed, but the detail lists `second write` first. `model::load_comments` sorts by authored `created`, then comment IRI; a process-local mint sequence only breaks equal timestamps, and cannot correct a clock offset. The test asserts the observed inversion, not the desired future behavior. It models clock skew and shared durable state, not actual network replication. The skew also makes the later write's item `modified` earlier than its filing; consequences for other views require separate tests.

## Inventory of decisions

The clock is the invoking kernel's `Clock` through `now_ms` (`src/endpoints.rs`); a host may supply `SystemClock` or an injected clock. No direct system-clock read was found in `src`. Imported dates are caller claims validated against that kernel clock, and backfilled dates are approximations. They are not independent clock measurements. References below are entry points, not an assertion about dependent crates or host applications.

| Decision | Inputs and consequences | Cross-host boundary |
| --- | --- | --- |
| Item listing and `next` | `src/model.rs` orders by `modified`, falling back to `created`, then number; `endpoints/listing_sort.rs` also offers created and modified sorts. `policy.rs` kata ranks priority then newest modified; the aging policy computes age from created and kernel now, and uses created as a tie-break. Imported authored dates participate. | Items from different writers or ledgers can be ranked together. A slow writer can make a later update look older. Offset pages can shift when keys change; they are not timestamp cursors or snapshots. |
| Comment order and last comment | `model.rs` orders comments by created and IRI; the JSON `comments=last` path takes maximum created and an IRI tie-break. Search excerpts also read comments in created order. | Comments on the same shared item can come from differently clocked hosts or importers. “Last” can select an earlier write. |
| History | `endpoints/history.rs` sorts event created time then ID, including claimed historical dates. | Events written by multiple hosts or imported afterward can appear in a different order from commits. The time order may be useful as source chronology, but does not prove causality. |
| Session attachment and listing | `endpoints/session.rs` selects the newest hand-back by comment created and IRI when attaching a summary; session lists and offset pages sort by summary created. Summary created is kernel time. | A slow host's later hand-back can lose to an older one, attaching a summary to the wrong hand-back. Session summaries may originate on different hosts. |
| Leases and stale work | `claim.rs`, `select.rs`, `endpoints/lapse.rs`, `endpoints/flight.rs` and `doctor/*.rq` write expiry from the granting kernel clock and compare it with the reading kernel's now; stale awaiting uses `awaitingAt`, or a newest-comment fallback, and age. Cache deadlines use the same comparisons. | A fast observer can report a lease expired early; a slow observer can report it live late. Skew affects stale-work findings and their cache deadlines too. Claim epochs fence superseded claims, but do not make elapsed time accurate. |
| Date validation and provenance | `attribution.rs` rejects claimed future dates against kernel now, checks modified against created, and checks dated events against filing and sometimes the target's filing. Claimed modified provenance is compared with the stored value (`model.rs`); undated writes stamp kernel time. | A slow host may reject a valid source date, and mixed-clock comparisons can misstate chronology or provenance. |
| Daily counts | `endpoints/counts.rs` buckets filing and status events by UTC day, sorts status events by `(time, eventSequence, status)`, and refuses a status event before filing. Backfill derives approximate dates from existing values. Today comes from kernel now. | Cross-host skew can move events to a different day, reorder close/reopen transitions, or cause the before-filing refusal. This is a UTC reporting series, not a daily spending budget. |
| Close evidence and ledger link mirrors | `endpoints/evidence.rs` finds the standing status by `eventSequence`, not by date. `endpoints/across.rs` uses a subject snapshot's count of status and link edit events as `mirrorVersion`, with a conditional update to reject older versions. Imported history-only events are excluded. | These are scoped to one shared subject/store history, not a general merge protocol for independently diverged stores. A crash or missing grant can leave a mirror stale, as the source documents. Equal versions from divergent replicas would not establish an order. |
| Other time decisions | `raised` is a caller-supplied date for age-oriented queries (`vocabulary.ttl`); identifiers include a timestamp plus process nonce and sequence (`endpoints.rs`), but are not a cross-process ordering authority. Lapse listings sort by expiry. | Supplied dates and IDs can travel with records; neither establishes commit order across hosts. |

The repository has offset paging and a host-facing snapshot/feed protocol, but this review found no timestamp cursor implementation or per-day budget in `src`. Store query time budgets belong to the store, not a ledger daily quota. This inventory covers decisions in this repository; it cannot establish absence of time decisions in a host, judge, gonk, store, or core.

## Proposed contract

**Accepted 2026-11-24 (Brian):** the four rules below are the contract, and the follow-up items at the end are filed in the ledger.

1. Give each authoritative aggregate a durable, atomically assigned revision in its serialization domain. For a shared store, allocate a per-item sequence in the same transaction as the mutation; persist it across restarts and use it for actual commit order, standing hand-backs, and state transitions. A process-local counter or a timestamp plus random ID gives uniqueness or a deterministic tie-break, not a global order. Declare whether ordering is per item or per ledger; do not compare unrelated per-item sequences as a global clock.
2. For independently writable replicas, a local sequence alone cannot order concurrent records. Carry a stable writer ID, durable sequence, and causal context (or a hybrid/logical clock with a deterministic writer/ID tie-break); define conflict semantics explicitly. A total tie-break makes convergence deterministic but does not prove which concurrent event happened later. Corrections should reference the verdict they supersede and authorization should be checked, rather than selecting whichever wall time is largest. Specify duplicate delivery, offline writes, rollback, and replica reset before implementing a merge.
3. Retain wall time and its source for display, source chronology, and calendar reports; distinguish authored time from commit time. Neither is authoritative for causal order. Preserve imported historical chronology as a separately labeled view. For legacy data without a sequence, keep the existing deterministic order as an explicitly approximate fallback; never invent causality. Version the schema and API, backfill only where order is provable, and test mixed old/new records and pagination migration.
4. Leases need a time authority, not merely a logical clock: use one lease authority's clock and atomic fencing epochs, or explicitly bound skew and account for it conservatively. A monotonic clock is useful for local elapsed durations but cannot be persisted or compared across reboots/hosts without a defined mapping. Document availability and safety tradeoffs during partitions. Calendar budgets, if implemented in a host, should key by a declared IANA zone and local date, with explicit DST, zone-change, and shared-authority rules; do not silently use the observer's zone. Existing UTC counts should retain their documented semantics unless deliberately versioned.

## Proposed follow-up items

- **Sequence ledger mutations in the store.** Design atomic per-item revisions, concurrent writes, legacy fallback, and versioned history and last-hand-back reads; add skew and restart tests.
- **Make lease time authority explicit.** Specify skew bounds or a single authority, fencing, partition behavior, and cache expiry; test fast and slow observers.
- **Specify replicated record reconciliation.** Inventory judge verdicts, corrections, gonk mirrors, and their cursors in their owning repositories; define causal identifiers, correction references, concurrency and duplicate handling before choosing a clock.
- **Separate source chronology from commit order.** Design compatible history, counts, listing and paging semantics for imported dates and mixed legacy records; reproduce skewed close/reopen and daily counts.
- **Define calendar budgets at their owner.** Inventory daily quotas and clock sources, then specify declared zones, DST, zone changes and shared counters with boundary tests.
